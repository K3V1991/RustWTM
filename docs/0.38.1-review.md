# RustWTM 0.38.1 release scope and validation

## Scope

Fixes found by running App power against the real power plan on the
developer host, and a safer PowerShell uninstaller. Protocol 20 is
unchanged; a 0.38.0 service and a 0.38.1 window work together.

- **A plan already in use.** On a machine already on High performance,
  each game logged "power plan High performance for game mode" and
  "power plan High performance again", wrote `power-plan.txt` and set the
  same plan again. The keeper now only notes that the plan is in force:
  nothing is switched, saved or logged, and a plan the user chooses
  meanwhile is still kept.
- **A request after an override.** When the user chose another plan while
  an entry was active, the plan RustWTM had applied stayed recorded. The
  next request that came straight after (a game starting while the entry
  still ran) was taken for another override and never served. The
  override now drops it; the next request switches as usual and gives the
  user's plan back. The *App power* page no longer names RustWTM's plan
  once the user chose another.
- **PowerShell uninstaller.** `uninstall.ps1` checks that the installation
  is its own (the service's executable path) before it stops services or
  removes files, closes only programs from that installation, takes
  `-InstallDir` for a custom script installation, handles paths with
  brackets literally, and stops before removing files when native cleanup
  fails, so a retry still finds them.

## Verification

`cargo fmt --check`, `cargo clippy --workspace --all-targets -D warnings`,
`cargo doc` with warnings denied and the workspace tests pass on the
developer host (1246 passed, 23 ignored), as does
`scripts/ci/test-uninstall-lifecycle.ps1`.
`scripts/ci/verify-release.ps1 -Tag v0.38.1` checks the
published assets. CI adds 0.38.0 as an upgrade baseline, with the SHA-256
of its published MSI.

The live check that found the two keeper faults ran the installed 0.38.0
service with an entry for a renamed copy of `ping.exe` asking for
Balanced and keeping the computer awake, read through the service's own
status and events. The switch, the saved plan, the plan given back after
the hold and a plan chosen meanwhile behaved as designed; the details are
in the [0.38.0 review](0.38.0-review.md). The configuration was restored
byte for byte afterwards.

New tests:

- `wtm-service`: a plan already in use is neither switched nor given back
  (and another plan asked for later switches and comes back to it, and a
  plan the user chooses meanwhile is kept); a request after an override is
  served; the window names no plan after an override. Each fails on
  0.38.0's keeper.
- `wtm-gui`: the test data's sample stays current however long a test
  runs. On a slow CI runner the out-of-date banner appeared between
  finding a row and clicking it, and a click test missed its row.
- `scripts/ci/test-uninstall-lifecycle.ps1` (CI and release): the
  uninstaller's ownership checks and teardown order against fake
  processes, registry, native commands and files.
- `wtm-service`: the core placement batch test no longer depends on the
  test runner's own process ID.

Not covered: the fixed keeper running as the installed service (0.38.1's
tests use a machine in memory); a machine with Modern Standby and a
single plan.
